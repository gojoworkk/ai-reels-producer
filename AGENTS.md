# AGENTS.md — правила для AI Reels Producer

## Что это
Личный инструмент для одного пользователя (владельца). Берёт Instagram-аккаунты конкурентов, тянет их последние 20 рилсов, ранжирует по просмотрам, достаёт сценарий ролика и переписывает его на русском под нас.

## Главное правило: максимально лёгкая система
- Один пользователь — это владелец. Никаких регистраций, ролей, команд, мультитенантности, OAuth.
- Никакого enterprise: без микросервисов, очередей (Celery/Redis/Kafka), Docker-оркестрации, DI-фреймворков, абстрактных слоёв «на вырост», фича-флагов, i18n-систем, кэшей, rate limiter-ов, метрик и логирования уровня продакшена.
- Не решаем задачи, которых у одного пользователя нет. Сомневаешься, нужно ли — не делай.
- Минимум кода. Три похожие строки лучше, чем преждевременная абстракция. Новый файл, зависимость или таблица — только если без них нельзя.
- Простая аутентификация: один секретный токен/пароль из `.env` (или вообще только localhost).
- Фоновые задачи — простой встроенный механизм (FastAPI BackgroundTasks / поток), не отдельная инфраструктура.
- Ошибки: показать понятное сообщение в UI. Без сложных retry-стратегий.

## Стек (по схеме «Reels Finder — как устроено внутри»)
1. **Источник данных:** Instagram-аккаунты конкурентов → Apify (парсинг последних рилсов).
2. **Front-end:** Next.js. Экраны: «Конкуренты», «Главное» (таблица рилсов), «Карточка рилса» (хук / скрипт / CTA с редактированием).
3. **API + Back-end:** FastAPI. REST + JSON. Бизнес-логика, сохранение данных, статусы обработки.
4. **База и хранилище:** PostgreSQL (конкуренты, рилсы, тексты, статусы) + файловое хранилище на диске (обложки, видео, превью, экспорты).

Сквозной процесс: добавил конкурента → Apify достаёт рилсы → backend нормализует → пишет в БД и хранилище → front показывает список → открываю рилс и редактирую текст → backend сохраняет → данные обновляются в приложении.

## Решения владельца
- **Без сервера.** Денег на хостинг нет, всё работает локально на компьютере владельца. Никакого деплоя, доменов и облака.
- **AI через Claude CLI, а не через API-ключ.** Backend вызывает `claude -p` как внешнюю команду; тратятся токены сессии/подписки. Ключ Anthropic не нужен.
- **Vercel не используем.** Сейчас только локально, сервер (VPS) добавим позже. Чтобы переезд был лёгким, без усложнения кода: адрес БД и папка файлов берутся из `.env`, а вызов Claude CLI лежит в одной функции (потом её можно заменить на API).
- **Код пишем с нуля.** Прежняя реализация из git-истории не используется как основа: она не понравилась владельцу.

## Модели и режимы (Claude меняет их сам под задачу, чтобы тратить меньше токенов)
Начинаем с Medium, режим повышаем только после ошибки. Max и Fable не используем без крайней нужды.

| Задача | Модель | Режим |
|---|---|---|
| Каркас, запуск одной командой | Sonnet 5.5 | Medium |
| База и хранилище | Haiku 5.5 | Medium |
| Apify и загрузка 20 рилсов | Sonnet 5.5 | Medium (High, если формат запутанный) |
| Экраны: Конкуренты, Главное, Карточка рилса | Sonnet 5.5 | Medium |
| Дизайн по референсам | Sonnet 5.5 | Medium |
| Мой профиль | Haiku 5.5 | Medium |
| Расшифровка речи (Whisper) | Opus 5.5 | High (Extra, если застрянем) |
| Remix через Claude CLI | Sonnet 5.5 | High, потом Medium |
| Экспорт PDF/CSV, автообновление | Haiku 5.5 | Medium |

Внутри продукта (`claude -p --model ...`): разбор на хук/скрипт/CTA — Haiku, перевод и адаптация под владельца — Sonnet.

## Дизайн
Референсы от владельца: чёрно-белый минимализм, мягкие светло-серые фоны, большие скруглённые карточки, чёрные «таблетки»-кнопки, плавные тени, много воздуха, чёрные акцентные блоки. Без ярких цветов, без лишних иконок и декора.

## Как работаем
- **Поэтапно.** План в `PLAN.md`. Один этап — один законченный, запускаемый результат. К следующему этапу не переходим без «ок» владельца.
- Владелец не разбирается в API-ключах, хостах и инфраструктуре. Всё настраиваем сами максимально просто: один `.env`, одна команда запуска, готовые значения по умолчанию. Если нужен ключ — объясняем по шагам, где его взять, простыми словами.
- Язык интерфейса, сценариев и общения — русский.
- Сценарии на русском должны быть адаптированы «под нас» (ниша, тон и аудитория берутся из короткого профиля, который задаёт владелец), а не просто переведены.
- **Репозиторий публичный (GitHub не даёт приватный), поэтому в git не попадает ничего личного.**
  - Секреты только в `.env`, `.env` не коммитим. В репозитории лежит только `.env.example` с пустыми значениями.
  - В `.gitignore`: `.env`, база (`pgdata/`), хранилище файлов (`storage/`), экспорты, логи.
  - Личные данные (список конкурентов, «Мой профиль», сценарии, видео) живут только в БД и хранилище, никогда в коде, примерах или тестах.
  - Ключи и токены не вставлять в код, комментарии, документы и сообщения коммитов.
  - Перед каждым коммитом проверять `git diff --staged` на секреты и личные данные.
  - Если ключ всё же попал в git, его немедленно перевыпускаем: удаления из истории недостаточно.
- Коммитим только по просьбе владельца.
